# Fit LUTs to real photos (`photoFit`)

A GR IV `.cube` import switch, **on by default for new imports**. Presets already in a project keep
how they were fitted, so nobody's existing looks change until they import a `.cube` again. With the
switch off, every import is byte-for-byte what 0.8.15 makes.

## Why

A `.cube` cannot run in the camera as it is: GR Mod fits the slot's matrix, three curves, post
matrix and hue sectors so that the camera comes as close to the LUT as it can. Where the fit puts its
effort depends on the colours it is fitted on. Today those are the calibration colours, a synthetic
set and a 9³ grid, which look little like photographs (issue #23: about 5× the purples, about half
the neutrals and skin of real pictures). So the error tends to land where people look most: skies,
greys, faces.

## What it does

`core/src/color/photo-fit.ts`, `photoWeightedFit` in `convert.ts`:

1. Same default fitting colours, plus, each repeated for weight:
   - 4096 pixels of real photographs (Kodak Lossless True Color Image Suite, the odd-numbered
     pictures; `photo-samples.ts`, generated by `tools/photo-fit/make_samples.py`),
   - blue sky (200 colours), a 256-step grey ramp and skin at four exposures (the refinement's
     guard sets), and in two weightings pale bright colours (clouds, white walls).
2. Four weightings (`PHOTO_WEIGHTINGS`) are fitted. They are the ones that won most often when the
   same idea was tuned one LUT at a time against held-out raw photos.
3. The fit closest to the LUT on colours none of them was fitted on — 4096 pixels of the
   even-numbered Kodak pictures plus an offset sky set — is kept, **only if** it beats the default fit
   there by at least 0.02 CIEDE2000 and greys, skin and sky get no worse (+0.05 / +0.1 / +0.05).
   Otherwise the default fit stands. Hue sectors follow as before.

The switch is under the Image Control features ("Fit LUTs to real photos") and applies to `.cube`
presets imported from then on. Each preset remembers in the project whether it was imported with it.
A photo-weighted fit takes seconds, so its result is saved (`fit-<sha256>` in the app's storage, keyed
by the LUT text, the firmware and the options) and reused when the project is opened again, instead
of fitting again on every start.

## Results

20 LUTs (film emulations, ARRI looks, Leica / Fuji / Kodak / Hasselblad / RED looks), GR IV 1.20,
added slots (hue sectors on). Measured on **about 60 MIT-Adobe FiveK raw photos** (sky, portraits,
interiors, dusk; 34 camera models) rendered like the GR IV's Standard; the import never sees them.
Mean CIEDE2000 between what the camera model makes and what the LUT itself makes:

| | default | photoFit |
|---|---|---|
| all pixels | 1.54 | **1.35** |
| skin | 1.22 | **1.01** |
| blue sky | 1.92 | **1.70** |
| bright near-neutrals | 2.08 | **1.69** |
| pixels off by more than 3 | 10.6 % | **9.1 %** |

17 of 20 LUTs came out closer (largest gain 0.65); for 3 the default fit stayed, so they are
unchanged. One look (ARRI Film A) is closer overall and on skin but 0.24 further on FiveK skies.

Note: the four weightings were found earlier by tuning against these same photos one LUT at a time;
the choice between them in the import uses only the Kodak and synthetic colours above. Tuned by hand
per LUT, the earlier result on 15 of these LUTs was 1.45; the automatic option gets 1.42.

Import time with the switch on: about 11 s per LUT on a laptop (40 s for the slowest), against
1.5 s, once per LUT; it runs in the worker with the progress bar.

To reproduce: `tools/photo-fit/evaluate.ts` (the test photos are not in the repository; any set of
Standard-rendered pixels with sky / skin masks works).
